# ALR: Classic alert mapping (all 188 `AlertType`s)

> Format (PRD §7): `- **ID** {Mn} [M][W][P] statement (source)`. Tags: `[UI]` = covered by app or UI tests; `[manual]` = covered by a QA-REPORT row.

## 1. Purpose

The C# port routes every message, consent prompt and outcome through one modal, `FormAlert.Alert(AlertType, …)` (`Form_Alert.cs:262-835`). Parsec Merchant has no such catch-all. This spec maps **every** case of `enum AlertType` (`Enums.cs:30`, **188 cases**, counted by script) to exactly one new home, by name, in `Enums.cs` order. The app's exhaustive-switch test (PRD §8.2, M9) asserts that the mapping is complete.

**Two sides of each requirement.**
- **Engine side.** The typed value exists in `ParsecEngine` and is emitted or returned at the right moment. It is tested at the milestone in the `{Mn}` tag:
  - `{M2}`: cargo, equipment, ship, bank and crew validation and consent;
  - `{M3}`: travel, arrival, encounters, police and combat;
  - `{M4}`: quests, tribbles, reactor, antidote, Wild, Jarek, Princess, sculpture and the other special events;
  - `{M6}`: persistence, file errors, high scores and game end.
- **Presentation side.** The app routes the value to the presentation listed here. This side is verified for **all** rows in M9 by the exhaustive-switch test.
- Rows that are presentation-only or removed are tagged `{M9}`. Their requirement is satisfied when the M9 test proves that nothing in the app or engine raises them, and that their replacement (named in the row) exists.

## 2. Classes

| Class | Engine type (PRD §6.2) | Meaning | New presentation |
|---|---|---|---|
| **CommandError** | `StepResult.rejection: CommandError` | Validation. The command is rejected and **no state changes**. The app also asks `preview(_:)` up front so the control is disabled before the player tries. Two advisory alerts that blocked nothing (`ShipBuyIFTransfer`, `TribblesTradeIn`) map to a `preview` note rendered the same way, and are counted here. | Inline reason: a disabled control plus a help tag and footer text. Never a modal. |
| **Confirmation** | `StepResult.decision = .confirm(Confirmation)` keyed by `WarningID`, resolved by resending with `acknowledging:` | Two-phase consent. The first call changes nothing; the acknowledged resend performs the action. Decisions the engine raises by itself mid-flow (the scoop canister) use their own `PendingDecision` case. `GameAbandonConfirm` is app-layer only (`AppConfirmation`). | `confirmationDialog(item:)` that states the consequence. Destructive or illegal choices get the destructive role and are never the default. |
| **GameEvent** | `StepResult.events: [GameEvent]` (and the `gameOver` decision for endings) | An outcome that has already happened. Each one is posted to the event feed and the Captain's Log, and grouped into the arrival report when it happens in transit. Rows marked **GameEvent (critical)** force a **report sheet** instead of the non-modal card (UX-VISION §5.3: arrest, escape pod, insurance payoff, reactor meltdown warning, game over). Sub-events emitted in the same step as a critical event appear as sections of that sheet. | Feed + log, the arrival report, the combat log, a report sheet, or the game-over card. |
| **Narrative** | `GameEvent.narrative(Narrative)` | Special-event and quest story text: the result page after accepting an event, and passenger chatter. | Narrative sheet (UX-VISION §5.4) or a "Ship's comm" feed + log entry. |
| **SystemAlert** | App layer only (`ParsecPersistence` errors) | File and version errors. | Standard `alert(item:)` with a recovery suggestion. |
| **Removed** | none | Never raised, splash or presentation-only, or cheat-only. Each row states the reason and what replaces it. | None. |

**Wording.** All new labels are plain and modern ("Stop", "Cancel", "Leave It"), not the classic "Int.", "OK, I Won't" or "Forget It". Classic titles and buttons are quoted only for traceability. Player-facing text is localized in `Localizable.xcstrings`. The engine carries only typed values and parameters (PRD §6.2).

## 3. Method and verification

- The case list was extracted by script from `Enums.cs:30-220`. Count = 188, all unique, and each has exactly one `case AlertType.X:` in `Form_Alert.cs` (the line cited per row).
- "Raised at" lists every `AlertType.X` reference in all 54 `.cs` files, except:
  - `Form_Alert.cs`, which holds the definitions;
  - `Form_Test.cs`, a developer harness that iterates every type (`Form_Test.cs:61`) and shows a generic `Alert` (`Form_Test.cs:265`).
- Line comments and `/* … */` blocks are excluded. `TravelArrival` occurs only inside a block comment (`Game.cs:3199-3202`).
- Two raises go through a variable. They are listed as "assigned; shown at":
  - `GameEnd` assigns `alertType` (`Form_SpaceTrader.cs:2805-2816`) and shows it at `Form_SpaceTrader.cs:2819`;
  - `EncounterMeet` assigns `initialAlert` (`Game.cs:1395-1424`) and shows it at `Game.cs:1428`.
- **14 types are never raised:** CargoNotSold, ChartTrackSystem, ChartWormholeUnreachable, EncounterDumpAll, EncounterPostMarie, GameClearHighScores, GameEndBoughtMoonGirl, JailFleaReceived, NewGameConfirm, NewGameMoreSkillPoints, ShipBuyNotAvailable, ShipDesignIF, SpecialNotEnoughBays and TravelArrival. This matches research 02 §4.
- **The 46 special-event texts** do not use `AlertType`. `Form_SpaceTrader.cs:3615-3655` builds them straight from `SpecialEvent.Title`/`.String`. They become `PendingDecision.specialEvent` and are specified in QST, not here.
- **Ruleset tags.** Palm 1.2.2 has no Sculpture, Princess, Scorpion, disruptors, disabling, hidden compartments, shipyard designer or passenger impatience (PRD §4.4). Rows that depend on these features are tagged `[M][W]`. `GameEndBoughtMoonGirl` is `[M]` only (PRD §4.3).

**Deviations from UX-VISION §6** (each one argued in its row):
- `Egg` is kept as a GameEvent because it changes state (it adds a shield and clears the hold).
- `GameEndBoughtMoonGirl` comes back as a Modern ending.
- `OptionsNoGame` and `TribblesSqueek` are removed as presentation-only.
