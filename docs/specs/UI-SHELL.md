## Conventions (normative for every bullet below)

- **Localization.** Every user-visible string, including accessibility labels, help tags, menu titles and enum display names, comes from `SpaceTraderMac/Resources/Localizable.xcstrings` (`String(localized:)`, `LocalizedStringResource`, or a `Text` with a string-literal key). `Text(verbatim:)` is allowed only for data: commander, ship and system names and formatted numbers. Numbers use `.formatted()` and `.monospacedDigit()`. Completeness (no `new`/`stale` entries, pseudo-language run) is checked at M12 (A11Y/PRD §9 M12).
- **No `.popover`** anywhere in the app target (PRD §6.5, research 05 §4). Transient content uses an overlay, a sheet, the inspector or a `confirmationDialog`/`alert` from an optional item.
- **Accessibility identifiers.** Every interactive element (button, toggle, picker, text field, stepper, slider, table row, sidebar row, menu-bar item where SwiftUI supports it) has an `.accessibilityIdentifier`. Scheme: dot-separated lowerCamelCase segments `<scope>.<element>[.<qualifier>…]`, matching `^[a-z][A-Za-z0-9]*(\.[A-Za-z0-9]+)+$`. Qualifiers that name game data use the engine's Swift case name or index, never localized text: `TradeItemType` (`water`…`robots`), `ShipType` (`flea`…), `WeaponType`/`ShieldType`/`GadgetType` case names, `SkillType` (`pilot`, `fighter`, `trader`, `engineer`), `RulesetID` raw values (`modern`, `windows201`, `palm122`), `Difficulty` case names, crew id integers, slot indices, system indices. Identifiers are string constants in one app enum `AXID`; the UI-test target mirrors the ones it uses in `SpaceTraderMacUITests/AXID.swift`. §18 lists every identifier a UI test uses.
- **Inline reasons.** A control that the engine would reject is disabled, and its help tag (`.help`) and, where the layout has one, its footer text show the localized `CommandError` reason (UX-VISION §1.2, ALR §2 "CommandError"). Rejections never open a modal.
- **Presentation from engine values.** Confirmations (`PendingDecision.confirm(Confirmation)` keyed by `WarningID`) are presented as the ALR §4 row for that `WarningID` says; the destructive button gets `role: .destructive` exactly when the ALR row marks it "(destructive)", and Cancel is the default action for every destructive dialog.

## 1. GameSession and presentation state

- **UI-SHELL-001** {M7} [M][W][P] `GameSession` is an `@Observable @MainActor final class` created once per app launch and injected through the environment into every scene. It owns: `engine: GameEngine?` (nil = no game loaded), `mode: SessionMode`, `gameID: String?`, `currentSlotID: String?`, `lastManualSaveDays: Int`, `feed: [FeedItem]`, `presentation: Presentation?`, `selectedSection: Section`, `marketSelection`, and the services `slotStore: SlotStore`, `highScoreStore: HighScoreStore`, `audio`, `haptics`, `achievements` and `flavor` (the last four are no-op stand-ins until M10/M11). No view holds a `GameEngine` or `GameState` copy that outlives a render. (source: PRD §6.5; UX-VISION §1.1)
- **UI-SHELL-002** {M7} [M][W][P] `SessionMode` has exactly the cases `.welcome`, `.playing` and `.gameOver(GameEndType)`. It is derived, never set independently: `.welcome` iff `engine == nil`; `.gameOver(t)` iff `engine.state.phase == .gameOver(t)`; `.playing` otherwise. A unit test drives New Game → retire (acknowledged) → Close Game and checks `.welcome → .playing → .gameOver(.retired) → .welcome`. (source: PRD §6.2 `GamePhase`; UX-VISION §2 "When no game is loaded")
- **UI-SHELL-003** {M7} [M][W][P] `GameSession.send(_ command: Command)` calls `engine.perform(command, acknowledging: [])` synchronously on the main actor and hands the `StepResult` to `apply(_:)`. `apply` (a) on `rejection != nil` stores it in `lastRejection` (shown as status text) and presents nothing; (b) on `decision == .confirm(c)` presents `Presentation.confirmation(PendingConfirmation(command:, confirmation: c, acknowledged:))`; (c) on any other decision presents the route of UI-SHELL-006; (d) appends every event to the feed (UI-SHELL-008) and (e) runs the persistence triggers of SAV-038/SAV-046 and the high-score recording of SCORE-037. Tested with a fake `GameEngine` state for each branch. (source: PRD §6.2 "Two-phase confirmations", §6.5 "Engine calls are synchronous")
- **UI-SHELL-004** {M7} [M][W][P] Confirming a `PendingConfirmation` resends the same command with `acknowledging` = the warnings already acknowledged for this command plus the new one. If the engine answers with a further confirmation (for example `.useSingularity` then `.wildLeavesWithoutLaser`, or `.buyShip` then a Wild warning), the next dialog is presented and the set keeps growing, so no confirmed warning is asked twice. Cancelling any dialog drops the command and changes nothing. A unit test runs a chain of two confirmations and checks the second `perform` carries both warnings. (source: GameEngine.swift `perform(_:acknowledging:)`; TRV-021; ALR §2 "Confirmation")
- **UI-SHELL-005** {M7} [M][W][P] `Presentation` is an `Identifiable` enum with the cases `confirmation(PendingConfirmation)`, `appConfirmation(AppConfirmation)`, `systemAlert(SystemAlert)` and `sheet(SheetRoute)`. At most one is presented at a time; a new one replaces nothing but waits in a FIFO queue `pendingPresentations` until the current one is dismissed. `AppConfirmation` has the cases `discardUnsavedGame` (ALR-094), `revertToAutosave`, `deleteSlot(String)`, `loadImportedSave(String)`, `clearHighScores(RulesetID)`, `timewarpLoad(reloaded: Bool)` (CHEAT-046) and `closeGame`. `SheetRoute` has `newGame`, `openSavedGame`, `gameOptions`, `findSystem`, `shipPurchase(ShipPurchaseRequest)`, `retire(PendingConfirmation)`, `cheatConsole`, `decision(PendingDecision)` and `encounterInterim`. (source: UX-VISION §1.2 "Never stack modal dialogs"; ALR §2)
- **UI-SHELL-006** {M7} [M][W][P] `PresentationRouter.route(_ decision: PendingDecision, state: GameState, command: Command, acknowledged: Set<WarningID>) -> Presentation` is a pure function with an exhaustive `switch` (no `default`); `command`/`acknowledged` are what a confirmation resends: `.confirm(c)` → `.sheet(.retire(pending))` for `.retire`, the open ship-purchase review for `.buyShip` (UI-SHELL-072), otherwise `.confirmation`; `.tradeInOrbit`, `.plunder`, `.scoop` and `.newspaper` → `.sheet(.decision(_))`. A unit test calls it with one value of every case and of every `WarningID`. The exhaustive ALR-presentation test over all 188 rows is M9 (PRD §9 M9). (source: PRD §8.2 "routing for every PendingDecision"; ALR-104, ALR-137)
- **UI-SHELL-007** {M7} [M][W][P] Three pure, exhaustive text functions produce every engine-derived string: `ReasonText.text(for: CommandError) -> LocalizedStringResource` (all `CommandError` cases), `ConfirmationText.content(for: Confirmation, state: GameState) -> ConfirmationContent { title, message, confirmLabel, isDestructive }` (all `WarningID` cases; `amounts` interpolated as credits, systems or percentages as the ALR row says), and `EventText.text(for: GameEvent, state: GameState) -> LocalizedStringResource` (all `GameEvent` cases). Each is a `switch` without `default`; unit tests feed one fixture value per case and assert a non-empty English string, and assert `isDestructive` equals the ALR "(destructive)" marking for every `WarningID`. (source: CLAUDE.md "no user-facing strings" in the engine; ALR §4)
- **UI-SHELL-008** {M7} [M][W][P] Every `GameEvent` of an accepted step becomes one `FeedItem { id, day, systemIndex, entry }` (`entry` is `.event(GameEvent)` or an app `.note(FeedNote)` such as "Game saved.") appended in emission order, with `day`/`systemIndex` taken from the state after the step. The in-memory feed keeps the newest 500 items and is cleared when another game is loaded; it is not persisted (the persistent log is LOG, M10). Rejected commands and unacknowledged confirmations add nothing. (source: UX-VISION §1.2 "Outcomes go to the event feed"; PRD §6.5)
- **UI-SHELL-009** {M7} [M][W][P] Engine phases outside `.docked` in M7: after a `warp` or `jump` step the session shows the state the step ended in. If it ended `.docked`, the arrival events are in the feed. If it ended in `.encounter`, the detail area shows the interim encounter panel (UI-SHELL-010). If it ended `.gameOver`, the game-over card (UI-SHELL-097). The session never calls `perform` on a timer in M7 (auto-repeat is M9). (source: Travel.swift `warp`/`continueTransit`; PRD §9 M7 "Fully playable while docked")
- **UI-SHELL-010** {M7} [UI] [M][W][P] Interim encounter panel (replaced by UI-ENC in M9): a plain view with the encounter text ("At N clicks from X you encounter a … ", from `encounterStarted`/`encounterChanged` and `EncounterPreview.type`), both ships' hull and shield percentages from `GameEngine.encounterPreview`, and one button per `EncounterPreview.actions` entry (identifier `encounter.action.<EncounterAction>`), disabled with the localized reason when `rejection != nil`. Return triggers `defaultAction` when it is non-nil (ENC-132). Confirmations raised by actions follow UI-SHELL-004. The panel lets any encounter be finished, so no M7 game can get stuck. (source: UX-VISION §5.2; ENC-130…132, ENC-186)
- **UI-SHELL-011** {M7} [UI] [M][W][P] Interim decision sheets (replaced by UI-ENC in M9): `.tradeInOrbit(offer)` shows item, unit price, available and maximum quantity with a stepper and Trade / Decline (sends `.resolveTradeInOrbit(quantity:)`, 0 to decline); `.plunder` lists the victim's cargo rows with steppers and Take buttons (`.plunderTake`) and Done (`.plunderDone`); `.scoop(item)` is a confirmation dialog Pick It Up / Leave It (`.resolveScoop(accept:)`, ALR-070/071); `.newspaper(paper)` lists the masthead and headlines as plain text with Close. Identifiers `decision.trade.quantity`, `decision.trade.accept`, `decision.trade.decline`, `decision.plunder.take.<TradeItemType>`, `decision.plunder.done`, `decision.newspaper.close`. (source: ECO-081; ALR-052, ALR-070, ALR-071; UX-VISION §5.2 "Sub-flows")
- **UI-SHELL-012** {M7} [M][W][P] While `presentation != nil` or a sheet is shown in the main window, `GameSession.isModal` is true; MENU uses it to disable game commands (MENU-006). Dismissing the last presentation sets it false. (source: UX-VISION §1.2)
- **UI-SHELL-013** {M7} [UI] [M][W][P] Launch sequence: (1) parse launch arguments (`LaunchOptions.parse(_ arguments: [String], isDebug: Bool)`, pure) per CHEAT-047…051; (2) `-PMResetState` wipes per CHEAT-051 before anything is read; (3) create `SlotStore`/`HighScoreStore` at `Application Support/Parsec Merchant/` in the sandbox container; (4) `-PMScenario` starts its fixture per CHEAT-049, otherwise the main window opens in `.welcome`. No game is loaded automatically; Continue is one click on Welcome (UI-SHELL-021). (source: PRD §6.4, §6.5; UX-VISION §2)

## 19. Notes

- **Engine additions** (UI-SHELL-116…123): `GalaxyCode`, `ShipQuote.blocker`, `GameState.equipmentMarket`, `GameState.questLog`/`QuestLogEntry`, and the flag `questLogOrder`. SHP-077/079 already describe the equipment-market and ship-blocker previews as `preview(.equipmentMarket)`/`preview(.shipyard)`; the implementation exposes per-item queries instead (`equipmentBuyPrice`, `shipQuote`), so these bullets add the missing aggregate and blocker without changing SHP's rules.
- **PRD refinement**: PRD §6.6 says the galaxy code encodes "ruleset plus seed". It also encodes the difficulty, because `generateUniverse` takes it, so two friends with the same code but different difficulties would otherwise get different galaxies (UI-SHELL-118).
- **Additions to UX-VISION §10.1** (owned by MENU): File › Close Game (the "Main Menu" action of the game-over card) and Game › Use Singularity (an action without a menu item would break UX principle 4).
- **Interim M7 surfaces** (UI-SHELL-010, -011, -097) keep a game playable end to end before the M9 encounter and event UX exists; UI-ENC replaces them and may reuse their identifiers.
- **C# quest-list quirks** (UI-SHELL-121) are kept in Modern too, because PRD §4.3's closed MOD list has no entry for them; whether Modern should fix them is an open question for the owner.
