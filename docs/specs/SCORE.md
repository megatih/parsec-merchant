# SCORE: Endings, score and high scores

> Format (PRD §7): `- **ID** {Mn} [M][W][P] statement (source)`. `[M]` Modern, `[W]` Windows 2.01, `[P]` Palm 1.2.2. A bullet carries only the tags of the rulesets for which it holds; differing values get separate bullets.
> Milestones: the endings, the Retire command and the score formula of Windows 2.01 / Modern {M4}; Palm-only variants and Modern-only fixes that need a ruleset flag {M5}; the high-score table and its storage {M6}; presentation {M7}/{M9}.
> C# sources are relative to `/Users/megatih/Downloads/SpaceTraderSource201`; Palm sources are `docs/reference/palm-src/Src/…`. Every number and order below was re-read from those lines on 2026-11-17. The worked examples in §5 were computed by hand from the source expressions and re-checked with a throw-away Int32 simulation.
> Notation: `D` = difficulty raw value (Beginner 0 … Impossible 4, `Difficulty.rawValue`); `days` = `commander.days`; `worth` = `GameState.worth` (C# `Commander.Worth`, Commander.cs:389-395; Modern/Palm definition per RUL-119); `/` is integer division truncating toward zero (C# and C agree); `%` is the C#/C remainder (sign of the dividend).
> Ownership: the quest that leads to the moon (buying it, the Utopia button condition) is QST-MOON; combat outcomes are CMB-044/CMB-048; the travel pipeline and the reactor meltdown are TRV-043/TRV-052/TRV-061; the escape pod is POL/BNK-047; cheats are CHEAT; saves, Ironman and `reloadCount` are SAV. This spec owns what happens once the game ends, the score and the high-score table.

## 1. Endings

- **SCORE-001** {M4} [M][W][P] The game has exactly three classic ways to end, the `GameEndType` cases `killed` (0), `retired` (1) and `boughtMoon` (2); a fourth case `boughtMoonGirl` (3) exists for the Modern cosmetic variant (SCORE-008). Raw values match C# `GameEndType` (C# `NA = -1` is represented by the phase not being `.gameOver`). (source: Enums.cs:404-412; Palm: Src/spacetrader.h:432-434)
- **SCORE-002** {M4} [M][W][P] An ended game is represented only by `state.phase == .gameOver(endType)`; there is no `PendingDecision` for the end (TRV-043, TRV-068). The step that ends the game commits its state changes, sets the phase, and its events end with `GameEvent.gameEnded(endType, score:)` (SCORE-012). (source: GameEndException.cs:33-36, Form_SpaceTrader.cs:2801-2841)
- **SCORE-003** {M4} [M][W] **Killed in combat.** When an encounter round leaves the player's hull ≤ 0 and the ship has no escape pod, the engine emits `.bothDestroyed` if the opponent's hull is also ≤ 0, else `.playerDestroyed`, then sets `phase = .gameOver(.killed)` (CMB-044). Because the player-destroyed branch is tested first, a both-destroyed round runs none of the victory effects (no bounty, no record or reputation change, no quest-ship kill status, no loot). With an escape pod the game does not end (POL escape-pod sequence). (source: Game.cs:1181-1192, :3142-3143)
- **SCORE-004** {M5} [P] **Killed in combat, Palm.** Palm tests "both hulls ≤ 0" first: with an escape pod the pod sequence runs, otherwise `.bothDestroyed` and `.gameOver(.killed)`; a lone player hull ≤ 0 likewise ends with the pod or `.playerDestroyed` and `.gameOver(.killed)` (CMB-048). The ending and its score are the same as SCORE-003. (source: Palm: Src/Encounter.c:941-1056, Src/Traveler.c:2446-2490)
- **SCORE-005** {M4} [M][W][P] **Reactor meltdown.** On an arrival with `quests.reactor == QuestStatus.Reactor.date` (20) the engine emits `.reactorMeltdown`, sets `quests.reactor = notStarted` (0) and, without an escape pod, sets `phase = .gameOver(.killed)`; no `.arrived` event follows and the rest of the arrival pipeline does not run (TRV-052; Palm TRV-061). With an escape pod the game continues. The ending is `killed` (there is no separate meltdown ending). (source: Game.cs:365-378; Palm: Src/Traveler.c:2244-2258)
- **SCORE-006** {M4} [M][W][P] **Retirement.** `perform(.retire)` (§3) ends the game with `phase = .gameOver(.retired)`. Retiring costs nothing and changes no other state: no day passes, no cash, debt or quest status changes. (source: Form_SpaceTrader.cs:3752-3760; Palm: Src/AppHandleEvent.c:143-146, Src/Traveler.c:2494-2499)
- **SCORE-007** {M4} [M][W][P] **Claiming the moon (Utopia).** Accepting the `MoonRetirement` special event (shown at Utopia while `quests.moon == QuestStatus.Moon.bought`, QST-MOON) sets `quests.moon = QuestStatus.Moon.done` (2) and ends the game with `phase = .gameOver(.boughtMoon)` in the same step. Its price is 0, so no cash changes; the score is computed after the status change, so `worth` still includes the 500,000 moon value (`quests.moon > notStarted`). (source: Game.cs:2388-2390, Commander.cs:393, Consts.cs:324; Palm: Src/SpecialEvent.c:195-199, Src/Money.c:48)
- **SCORE-008** {M5} [M] **Moon-girl variant.** In Modern only, when the `MoonRetirement` event is accepted while `quests.princess == QuestStatus.Princess.done`, the end type is `.boughtMoonGirl` instead of `.boughtMoon`; everything else, including the score (SCORE-018), is identical. It is driven by a ruleset flag (proposed `moonGirlEnding`, RUL-006), never by a ruleset-id test. Windows 2.01 and Palm always end with `.boughtMoon`. (source: PRD §4.3; Enums.cs:411 (defined but never assigned in C#))
- **SCORE-009** {M4} [M][W] `MoonRetirement` is not message-only, so it goes through `Command.specialEvent` with consent (`WarningID.acceptSpecialEvent`, `amounts == [0]`). The C# `CashToSpend < Price` check still applies: with Reserve Money on and `cashToSpend < 0` (BNK-054) the command is rejected with `.insufficientFunds` and the moon cannot be claimed until cash covers the reserved costs. (source: Consts.cs:324, Form_SpaceTrader.cs:3621-3651)
- **SCORE-010** {M5} [P] Palm's `ToSpend()` is never negative (BNK-055), so the Palm moon claim is never refused for funds. (source: Palm: Src/SpecialEvent.c:82, Src/Traveler.c:1234-1239)
- **SCORE-011** {M4} [M][W][P] No other path ends the game: arrest (even when the ship is sold), the escape pod, bankruptcy-level debt, the Gemulon invasion, the experiment and the tribble infestation all continue play. (source: Game.cs `GameEndException` is thrown only at :377, :2390, :3143 plus the Retire menu Form_SpaceTrader.cs:3756; Palm: `EndOfGame` is reached only from the Destroyed, Retire and Utopia forms, Src/Traveler.c:2446-2499)
- **SCORE-012** {M4} [M][W][P] Every game-ending step emits, as its last event, `GameEvent.gameEnded(GameEndType, score: Int)` where `score == state.score(for: endType)` evaluated on the committed state (SCORE-016). The earlier events of the step (`.playerDestroyed`/`.bothDestroyed`, `.reactorMeltdown`, `.specialEventCompleted(.moonRetirement)`) are unchanged. (source: Form_SpaceTrader.cs:2801-2822)

## 2. After the end

- **SCORE-013** {M4} [M][W][P] While `phase == .gameOver(_)`, `perform` rejects every `Command` with `CommandError.gameOver` and leaves the state unchanged, including `.setOptions`, `.track`, `.retire` and `.specialEvent` (C# disables the in-game menus and drops the game). (source: Form_SpaceTrader.cs:2803, :2839-2840, :2914-2924)
- **SCORE-014** {M4} [M][W][P] Read-only queries still work on a game-over state: `worth`, `score(for:)` and the commander/ship/quest views return the final values, so the app can build the game-over card from the state alone. (source: Form_SpaceTrader.cs:2819-2825)
- **SCORE-015** {M9} [M][W][P] The game-over presentation follows the C# order in one card (UX-VISION §5.5): the ending (killed / retired / moon / Modern moon-girl), then "You achieved a score of X.Y%" (SCORE-024/025), then the high-score outcome (SCORE-036). (source: Form_SpaceTrader.cs:2801-2841; Palm: Src/Traveler.c:341-375)

## 3. The Retire command

- **SCORE-016** {M4} [M][W][P] `perform(.retire)` is accepted only in phase `.docked`; in `.inTransit` or `.encounter` it is rejected with `.notAllowedInPhase` (the C# menu is unreachable behind the modal travel and encounter forms; Palm's Retire is a docked-form menu command). In `.gameOver` it is rejected with `.gameOver` (SCORE-013). (source: Form_SpaceTrader.cs:2914-2924, :3752; Palm: Src/AppHandleEvent.c:38-41, :143-146)
- **SCORE-017** {M4} [M][W][P] Two-phase consent: `perform(.retire)` without `acknowledging: [.retire]` returns `needsConfirmation(Confirmation(.retire, amounts: [state.score(for: .retired)]))` and changes nothing; with the acknowledgement it sets `phase = .gameOver(.retired)` and emits `[.gameEnded(.retired, score: state.score(for: .retired))]`. Retiring is allowed in debt and with passengers, quests or cargo aboard; none of these block it. (source: Form_SpaceTrader.cs:3752-3760, Form_Alert.cs:581-582; Palm: Src/AppHandleEvent.c:143-146)

## 4. Score formula

- **SCORE-018** {M4} [M][W] `GameState.score(for end: GameEndType) -> Int` is C# `Game.Score` with `EndStatus = end`:
  `W' = worth < 1_000_000 ? worth : 1_000_000 + (worth − 1_000_000) / 10`;
  `mod` = 90 (killed), 95 (retired), 100 (boughtMoon);
  `dm = end is moon ? max(0, (D + 1) × 100 − days) : 0`;
  `score = (D + 1) × mod × (dm × 1000 + W') / 250_000`, evaluated left to right in Int32: `((D+1) × mod) &* (dm &* 1000 &+ W')`, then `/ 250_000` truncating. In Modern `.boughtMoonGirl` uses the `boughtMoon` row (mod 100 and `dm`); C# would give 0 for it (no `case`), which is unreachable there. (source: Game.cs:4246-4269)
- **SCORE-019** {M4} [M][W] The Int32 product wraps exactly as C# (unchecked arithmetic): for `(D+1) × mod × (dm × 1000 + W') > 2,147,483,647` the score turns negative or wrong (on Impossible, retired: from `W' = 4,521,019`, i.e. worth ≥ 36,210,190). No MOD entry fixes this, so Modern keeps it. Negative worth (debt above ship price plus cash) gives a negative `W'` and a negative score, also kept. (source: Game.cs:4250, :4268)
- **SCORE-020** {M5} [P] Palm `score(for:)` is `GetScore`, with the same `W'` and `dm` but its own scale and truncation points: killed `(D+1) × ((W' × 90) / 50_000)`, retired `(D+1) × ((W' × 95) / 50_000)`, moon `(D+1) × ((W' + dm × 1000) / 500)`, each in 32-bit `long` (`W' × 95` wraps from `W' = 22,605,091`). The flag is `scoreFormula` (RUL-149). (source: Palm: Src/Traveler.c:178-195)
- **SCORE-021** {M4} [M][W] The score uses `worth` as defined for Windows 2.01: ship list price (`ShipSpec.price`, not hull, equipment or cargo) + cash − debt + 500,000 when `quests.moon > notStarted`. (source: Commander.cs:389-395, ShipSpec.cs:390)
- **SCORE-022** {M5} [M][P] Modern and Palm score with the trade-in worth of RUL-119 (`worthUsesTradeInValue`): trade-in value of ship and equipment (after repairs and fuel, with the tribble penalty) + cargo cost basis + cash − debt + moon. For a killed ending the trade-in value is taken from the final ship as the step leaves it (hull ≤ 0 counts against it through the repair term). [verify the Palm value at hull ≤ 0 with the harness] (source: Palm: Src/Money.c:48, Src/ShipPrice.c:72-90)
- **SCORE-023** {M4} [M][W][P] `days`, `worth` and `D` are read from the state at the moment the game ends (after the ending step's changes, SCORE-007), not at the start of the step. For the moon the days bonus `dm` counts the days still left before day `(D+1) × 100`; at or after that day it is 0. (source: Game.cs:4250-4263, Form_SpaceTrader.cs:2821-2825; Palm: Src/Traveler.c:305)
- **SCORE-024** {M4} [M][W] In Modern and Windows 2.01 `score(for:)` is already the score in tenths of a percent; there is no separate `scoreTenths` query in M4 (the Palm display variant is SCORE-025, {M5}). The app's display is `"\(t / 10).\(t % 10)%"` with the integer part grouped (C# `FormatNumber`, `{0:n0}`); for a negative `t` both parts carry the sign exactly as C# prints them (e.g. `-5969` → "-596.-9%", `-5` → "0.-5%"). (source: Form_SpaceTrader.cs:2821-2822, Form_ViewHighScores.cs:68, Functions.cs:98-101)
- **SCORE-025** {M5} [P] Palm `scoreTenths(for:) = score(for:) / 5` (C truncation), which reproduces Palm's display `a / 50 "." (a % 50) / 5` for every `a`, including negative ones; Palm prints the integer part ungrouped. Ranking (SCORE-031) uses the full Palm score, not the tenths. (source: Palm: Src/Traveler.c:343-350, :1269-1276)
- **SCORE-026** {M4} [M][W][P] `score(for:)` is a pure query usable in every phase (the Retire preview, the game-over card, the Commander inspector); they consume no RNG and change nothing. (source: Game.cs:4246-4269)

## 5. Worked examples

All examples are hand-computed from the expressions in SCORE-018 and SCORE-020 (W' = adjusted worth). C# = Modern/Windows score `s` (tenths), Palm = Palm score `a` and its tenths `a/5`.

- **SCORE-027** {M4} [M][W] Worked examples of `score(for:)`; each is a test case (`D, days, worth → s, display`):
  1. Killed, Normal (D=2), worth 11,000 (Gnat 10,000 + 1,000 cash): `3×90×11,000 = 2,970,000; /250,000 = 11` → "1.1%".
  2. Retired, Normal, worth 11,000: `3×95×11,000 = 3,135,000; /250,000 = 12` → "1.2%".
  3. Retired, Easy (D=1), worth 250,000: `2×95×250,000 = 47,500,000; /250,000 = 190` → "19.0%".
  4. Retired, Hard (D=3), worth 3,000,000: `W' = 1,000,000 + 2,000,000/10 = 1,200,000; 4×95×1,200,000 = 456,000,000; /250,000 = 1,824` → "182.4%".
  5. Killed, Normal, worth 999,999 vs 1,000,009: `W' = 999,999 → 3×90×999,999 = 269,999,730 → 1,079` ("107.9%"); `W' = 1,000,000 + 9/10 = 1,000,000 → 270,000,000 → 1,080` ("108.0%").
  6. Moon, Normal, day 150, worth 600,000: `dm = 300 − 150 = 150; 3×100×(150,000 + 600,000) = 225,000,000; /250,000 = 900` → "90.0%".
  7. Moon, Normal, day 300 and day 301, worth 560,000: `dm = 0` both; `3×100×560,000 = 168,000,000 → 672` → "67.2%" both.
  8. Moon, Beginner (D=0), day 250, worth 800,000: `dm = max(0, 100 − 250) = 0; 1×100×800,000 = 80,000,000 → 320` → "32.0%".
  9. Moon, Impossible (D=4), day 100, worth 2,000,000: `dm = 400; W' = 1,100,000; 5×100×1,500,000 = 750,000,000 → 3,000` → "300.0%".
  10. Killed, Normal, worth −5,000: `3×90×(−5,000) = −1,350,000; /250,000 = −5` → "0.-5%".
  11. Overflow: Retired, Impossible, worth 50,000,000: `W' = 1,000,000 + 49,000,000/10 = 5,900,000; 475 × 5,900,000 = 2,802,500,000` wraps to `−1,492,467,296; /250,000 = −5,969` → "-596.-9%".
  (source: Game.cs:4246-4269)
- **SCORE-028** {M5} [P] Palm worked examples (`a`, tenths `a/5`, display), same inputs as SCORE-027 where noted:
  1. Killed, Normal, worth 11,000: `(11,000×90)/50,000 = 19; ×3 = 57` → tenths 11 → "1.1%".
  2. Retired, Normal, worth 11,000: `1,045,000/50,000 = 20; ×3 = 60` → tenths 12 → "1.2%".
  3. Moon, Normal, day 150, worth 600,000: `(600,000 + 150,000)/500 = 1,500; ×3 = 4,500` → tenths 900 → "90.0%".
  4. Truncation differs from C#: Killed, Normal, worth 6,612: Palm `595,080/50,000 = 11; ×3 = 33` → tenths 6 → "0.6%", while C# `3×90×6,612 = 1,785,240; /250,000 = 7` → "0.7%".
  5. No overflow where C# wraps: Retired, Impossible, worth 50,000,000: `W' = 5,900,000; 560,500,000/50,000 = 11,210; ×5 = 56,050` → tenths 11,210 → "1121.0%".
  (source: Palm: Src/Traveler.c:178-195, :343-350)

## 6. High-score table

- **SCORE-029** {M6} [M][W][P] A high-score entry stores: commander name, end type, `score` (ruleset-native, SCORE-018/020), `days`, `worth`, difficulty, and, added by Parsec Merchant, the ruleset id, an Ironman flag (`state.ironman`) and a reloaded flag (`state.reloadCount > 0`). C# stores name, score, type, days, worth and difficulty; Palm stores name, status, days, worth and difficulty and recomputes the score from them, which gives the same value. (source: HighScoreRecord.cs:34-63, :90-102; Palm: Src/DataTypes.h:258-265; PRD §4.3, §8.3)
- **SCORE-030** {M6} [M][W][P] Tables are kept per ruleset (PRD §6.4); entries of different rulesets are never compared (their score units differ, SCORE-020). The ranking rule (SCORE-031) is the same in every ruleset (RUL "verified equivalences"). (source: PRD §6.4; HighScoreRecord.cs:65-88; Palm: Src/Traveler.c:310-312)
- **SCORE-031** {M6} [M][W][P] Ordering: entry `a` ranks above entry `b` iff `a.score > b.score`, or scores are equal and `a.worth > b.worth`, or both are equal and `a.days > b.days` (more days ranks higher on a full tie). Entries equal on all three compare equal. (source: HighScoreRecord.cs:65-88; Palm: Src/Traveler.c:310-311)
- **SCORE-032** {M6} [M][W][P] Capacity: the classic table has 3 slots (C# `new HighScoreRecord[3]`, Palm `MAXHIGHSCORE 3`); Parsec Merchant keeps the top 10 per ruleset (PRD §6.4). Insertion is the same in both: a candidate enters iff the table has a free slot or the candidate ranks strictly above the lowest entry (SCORE-031); a candidate equal to the lowest entry of a full table is not entered. When it enters, the lowest entry of a full table drops out. Consequently the first 3 entries of a 10-entry table always equal the 3-slot classic table built from the same sequence of games. (source: Form_SpaceTrader.cs:2771-2778, :2826; Functions.cs:137-145; Palm: Src/Traveler.c:301-337, Src/spacetrader.h:431)
- **SCORE-033** {M6} [M][W][P] Among entries that compare equal, the newer entry is placed below the older ones (Palm shifts down from the first strictly-worse slot). C# re-sorts with the unstable `Array.Sort`, which leaves equal entries in unspecified order; the deterministic Palm order is used for all rulesets. (source: Palm: Src/Traveler.c:310-327; Form_SpaceTrader.cs:2774-2775)
- **SCORE-034** {M6} [M][W][P] Eligibility: a game with `state.cheatsUsed` never enters the table, in every ruleset (PRD §8.3; C# `CheatEnabled`). The outcome is still reported as `excludedForCheats` when the score would have qualified, and as `missed` otherwise (the qualification test runs first, as in C#). (source: Form_SpaceTrader.cs:2826-2837; PRD §8.3)
- **SCORE-035** {M6} [P] Palm additionally excludes a game that was reloaded (Palm `GameLoaded`, set by the "Timewarp" load; in Parsec Merchant `reloadCount > 0`) per `highScoreBlock` (RUL-150): a qualifying score is reported as `excludedForReload` and not stored. In Modern and Windows 2.01 a reload does not exclude the entry; it is stored with the ↺ marker (SCORE-029). (source: Palm: Src/Traveler.c:331-332, :352-356, Src/WarpFormEvent.c:704-722; PRD §8.3)
- **SCORE-036** {M6} [M][W][P] `HighScoreTable.inserting(_ entry:, eligible:) -> (HighScoreTable, HighScoreOutcome)` is a pure value-type function in ParsecEngine; `HighScoreOutcome` is `.entered(rank: Int)` (1-based), `.missed`, `.excludedForCheats` or `.excludedForReload` (Palm). ParsecPersistence's `HighScoreStore` only loads and saves the table. (source: PRD §6.1, §6.4; ALR-098…100)
- **SCORE-037** {M6} [M][W][P] The app records the high-score entry exactly once per ended game, when it first observes `phase == .gameOver(_)` for that game; reopening an ended game does not insert it again. (source: Form_SpaceTrader.cs:2839-2840 (the game is discarded after `GameEnd`))
- **SCORE-038** {M6} [M][W][P] The table starts empty; "Clear High Scores" (Settings › Advanced, UX-VISION §2) resets a ruleset's table to empty after confirmation. C# has the routine and alert but no menu item; Palm has the menu command. (source: Form_SpaceTrader.cs:2795-2799, Form_Alert.cs:554-555; Palm: Src/AppHandleEvent.c:86-87, Src/Traveler.c:1308-1320)
- **SCORE-039** {M9} [M][W][P] Each table row shows rank, name, `scoreTenths` as "X.Y%" (SCORE-024/025) and the line "<ending> in <N day(s)>, worth <N credit(s)> on <difficulty> level." with endings "Was killed", "Retired", "Claimed moon" (Modern moon-girl: its own localized string), plus the Ironman badge and ↺ marker; empty slots show "Empty". All strings come from `Localizable.xcstrings`. (source: Form_ViewHighScores.cs:64-79, Strings.cs:141, :404-410; Palm: Src/Traveler.c:1256-1297)

## 7. Scenarios

- **SCORE-040** {M4} [M][W] Scenario (tests): (a) docked Normal game, `perform(.retire)` → confirmation `.retire` with the preview tenths, state unchanged; repeat with the acknowledgement → `.gameOver(.retired)`, last event `.gameEnded(.retired, score:)` matching SCORE-027 for the state's worth and days; any further command → `.gameOver`. (b) `.retire` during an encounter → `.notAllowedInPhase`. (c) combat round with both hulls ≤ 0 and no pod → `.bothDestroyed`, `.gameOver(.killed)`, no `.bountyPaid` and unchanged record; same with a pod → no game over. (d) arrival with reactor status 20 and no pod → `.reactorMeltdown`, `.gameOver(.killed)`, no `.arrived`. (e) moon bought, at Utopia, accept `MoonRetirement` → `quests.moon == done`, `.gameOver(.boughtMoon)`, score includes the 500,000 moon value and the day bonus; with Reserve Money on and negative `cashToSpend` → `.insufficientFunds`, nothing changes. (source: Game.cs:365-378, :1181-1192, :2388-2390, :4246-4269; Form_SpaceTrader.cs:3621-3651, :3752-3760)
- **SCORE-041** {M6} [M][W][P] Scenario (tests): starting from an empty table, insert entries with scores 500, 300, 300 (worth 10/20), 300 (worth 20, days 5 vs 9), 100 and check ranks, the equal-entry placement (SCORE-033), the strict "beats the lowest" rule on a full table, that a cheated qualifying game reports `excludedForCheats` and is not stored, that a Palm game with `reloadCount > 0` reports `excludedForReload`, and that the first 3 entries match a 3-slot run of the same sequence. (source: HighScoreRecord.cs:65-88; Form_SpaceTrader.cs:2771-2837; Palm: Src/Traveler.c:291-337)

## 8. API names proposed by this spec

- `Command.retire` (docked only; two-phase with the existing `WarningID.retire`; `Confirmation.amounts == [score(for: .retired)]`).
- `GameEvent.gameEnded(GameEndType, score: Int)` (SCORE-012).
- `GameState.score(for: GameEndType) -> Int` (decided; tenths of a percent in Modern/Windows). A Palm `scoreTenths(for:)` display variant is {M5} (SCORE-025).
- `HighScoreEntry`, `HighScoreTable.inserting(_:eligible:)`, `HighScoreOutcome { entered(rank:), missed, excludedForCheats, excludedForReload }` ({M6}).
- Ruleset flag `moonGirlEnding` (SCORE-008; RUL-006 names the behaviour but no flag).
- Existing names reused: `GamePhase.gameOver(GameEndType)`, `CommandError.gameOver`, `CommandError.notAllowedInPhase`, `CommandError.insufficientFunds`, `WarningID.retire`, `WarningID.acceptSpecialEvent`, `GameEvent.playerDestroyed`, `.bothDestroyed`, `.reactorMeltdown`.
- ALR-096/097/101…104 are aligned to the decided API: the phase `.gameOver(GameEndType)` (TRV-043) with `GameEvent.gameEnded(_, score:)`, and a payload-free `WarningID.retire` with the preview in `Confirmation.amounts`; the moon-girl ending is `GameEndType.boughtMoonGirl`.
